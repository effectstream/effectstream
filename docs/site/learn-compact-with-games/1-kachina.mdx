## Technical challenges

### Playing in the browser via WebAssembly

Midnight proving typically happens on the desktop or servers using a [Proof Server](https://docs.midnight.network/relnotes/proof-server).
While operating a proof server on your computer gives you the best performance, web3 users are often hesitant to install software on their local machines for security reasons.
Typically, this is intead solves by having dApps run proof servers on behalf of their users (the dApp author swallows the computation cost). For DeFi, which every operation pays fees to cover dApp operational costs, this makes sense. However, for games where there are many small transactions (each with low financial value yet potentially high compute cost such as submitting a move to a game), it is usually not financially viable for the dApp author to cover the compute costs.
Therefore, for games, it's cruical that we allow for users to generate proofs client-side *directly in their browser* (no need to download anything).

To achieve this, we compile the circuits using [WebAssembly](https://webassembly.org/). Notably, in this game, we achieve this using the [@paima/midnight-wasm-prover](https://www.npmjs.com/package/@paima/midnight-wasm-prover) package.

### Transaction sponsorship

Asking a new player to fund a wallet before their first move kills
onboarding. We cover the gas for player actions on the server side so the
game feels free at the point of use, while moves still settle on-chain.

### Commit-reveal moves

Players commit to a move first and reveal it later, so opponents can't react
to information they shouldn't see yet. We treat this as a stepping stone:
later games in the series replace it with stronger privacy primitives.

### Lobby system and global state

A lobby has to coordinate multiple players without each one sliding out of
sync. We model the lobby as global state and discuss how matches are opened,
joined, and finalized.
