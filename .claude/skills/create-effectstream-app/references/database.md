# Database: Migrations + pgtyped queries

`packages/database/` owns all SQL. The hard rule: **no raw SQL anywhere else in the codebase** except the one engine-internal recovery query in `config.ts` (NTP start-time recovery from `effectstream.sync_protocol_pagination` — see `references/chains/midnight.md` for the recovery pattern context).

Read this when scaffolding `packages/database/` or after changing the schema.

## Package layout

```
packages/database/
├── package.json
├── mod.ts                     # Re-exports queries + migrationTable
├── migration-order.ts         # Declares migration order via `migrationTable`
├── pgtypedconfig.json
├── migrations/
│   └── 000-init.sql           # Schema (CREATE TABLE, etc.)
└── sql/
    ├── queries.sql            # pgtyped query templates
    └── queries.queries.ts     # GENERATED by build:pgtypes — COMMIT THIS
```


## Sample pgtyped query

```sql
-- packages/database/sql/queries.sql
/* @name insertRoom */
INSERT INTO rooms (room_name, max_players, creator, block_height)
VALUES (:room_name!, :max_players!, :creator!, :block_height!);

/* @name getRoomByName */
SELECT * FROM rooms WHERE room_name = :room_name!;
```

`!` means required. After `bun run build:pgtypes`, `queries.queries.ts` exports `insertRoom` and `getRoomByName` as typed `PreparedQuery` objects.

## How to run pgtyped generation correctly

The `@effectstream/db/scripts/pgtyped-update.ts` script does everything in one shot: starts PGLite on port 5432, applies system + user migrations, runs pgtyped codegen, shuts down. It MUST be run with `packages/database/` as the working directory because it resolves three things relative to `process.cwd()`:

1. `migration-order.ts`
2. `pgtypedconfig.json`
3. `node_modules/@paima/pgtyped-cli/lib/index.js`

Two correct ways to invoke:

```bash
# Preferred — works from anywhere in the monorepo
bun run --filter @my-template/database pgtyped:update

# Or: cd into the package
cd packages/database && bun run pgtyped:update
```

### Always stop the orchestrator before running `build:pgtypes`

The pgtyped script starts its own PGLite on port 5432. If a previous `bun run dev` left an orchestrator daemon running (or any other process is holding 5432, 4747, 8545, 9999), the script fails or — worse — silently writes against the wrong DB. Run this **every time** before `build:pgtypes`, even if you think nothing is running:

```bash
bunx orchestrator stop || true
bun run build:pgtypes
```

`bunx orchestrator stop` (no process name) tells the orchestrator daemon on port 4747 to shut down every process it manages — including the PGLite, Hardhat, sync, batcher, and frontend. Without this, the next pgtyped run may collide with the previous boot's PGLite on 5432, produce confusing failures, or write a `.queries.ts` that reflects a stale schema. The `|| true` keeps the command from failing when no daemon is running.

Wire this into the template's `build:pgtypes` script so users never forget:

```json
"build:pgtypes": "bunx orchestrator stop > /dev/null 2>&1 || true; bun run --filter @my-template/database pgtyped:update"
```

The same rule applies to anyone running tests, restarting dev, or switching branches — stop the orchestrator first, regenerate types, then start the stack fresh.

## Common pgtyped mistakes that waste hours

1. **HAND-WRITING `*.queries.ts` instead of running `bun run build:pgtypes`. This is the worst class of bug.** The generated file contains a `locs` array — byte offsets into the SQL string where each `:param!` placeholder lives — that pgtyped uses to substitute parameter values. Off-by-N `locs` produce malformed SQL at runtime. Postgres rejects the statement, aborts the transaction, and **every subsequent query in the transaction returns `current transaction is aborted (code 25P02)`**, hiding the original error. The sync node then crashes. The file looks plausible on review (the `IQueryParams` interface, the doc comment, even the IR JSON all read fine) and TypeScript can't catch it. There is no shortcut — `locs` cannot be eyeballed or counted. ALWAYS run the script:

   ```bash
   bun run build:pgtypes
   # which expands to: bun run --filter @my-template/database pgtyped:update
   ```

   If you've already hand-written one and want to know if it's wrong, just regenerate it and `diff` — the answer is almost always "yes, every offset is wrong."

2. **Running from the wrong directory.** Without `--filter`, the script looks for `migration-order.ts` in the monorepo root, silently finds nothing, and emits empty `.queries.ts` files (or fails with cryptic errors).
3. **Port 5432 already in use (orchestrator daemon still up from a previous run).** Always `bunx orchestrator stop || true` before `bun run build:pgtypes` — see the section above. Bake it into the `build:pgtypes` script so users can't forget.
4. **Missing `@paima/pgtyped-cli` in devDependencies.** The script shells out to `node_modules/@paima/pgtyped-cli/lib/index.js`. Run `bun install` if missing.
5. **Forgetting to commit `*.queries.ts`.** Sibling packages can't import `@my-template/database` without them. Re-generate (don't hand-write!) and commit on every SQL change.

## How the rest of the codebase uses it

### Inside STM transitions

```ts
import { World } from "@effectstream/coroutine";
import { insertRoom } from "@my-template/database";

stm.addStateTransition("createRoom", function* (data) {
  yield* World.resolve(insertRoom, {
    room_name: data.parsedInput.roomName,
    max_players: data.parsedInput.maxPlayers,
    creator: data.signerAddress!,
    block_height: data.blockHeight,
  });
});
```

### Inside API routes

```ts
import { runPreparedQuery } from "@effectstream/db";
import { getRoomByName } from "@my-template/database";

server.get("/api/rooms/:name", async (req, reply) => {
  const result = await runPreparedQuery(
    getRoomByName.run({ room_name: (req.params as any).name }, dbConn),
    "/api/rooms/:name",
  );
  reply.send(result);
});
```

### Inside tests (Phase B `assertSQL`)

```ts
import { assertSQL } from "../helpers.ts";

await assertSQL(
  "createRoom: row appears with correct fields",
  db,
  `SELECT room_name, max_players, creator FROM rooms WHERE room_name = 'test-room';`,
  (res) => res.rows.length >= 1,
  (res) => res.rows[0].max_players === 4,
);
```

`assertSQL` is one of the few places in tests where raw SQL strings appear — it's a read-only assertion helper and is permitted in `packages/tests/helpers.ts`. Application logic still must use `PreparedQuery`.

## When raw SQL IS allowed

Just two cases:

1. **`packages/database/sql/*.sql` and `migrations/*.sql`** — source files.
2. **NTP start-time recovery from `effectstream.sync_protocol_pagination`** — the engine's internal table, not the application schema, so no pgtyped binding exists. See `references/multi-env.md` for the full snippet (it lives in `config.ts`).
3. **`assertSQL` in tests** — read-only assertion helper; OK in `packages/tests/`.

Everywhere else (STM transitions, API routes, batcher logic): use a generated `PreparedQuery`.
